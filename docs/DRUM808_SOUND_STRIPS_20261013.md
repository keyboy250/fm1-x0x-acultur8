# 808 track strips: local implementation and focused evidence

All eleven 808 tracks own one 68-byte shared strip and one 12-byte accumulating meter (880 bytes total). Configurations remain externally owned. `drum808_strip_meter_clear()` is an outer-engine-block hook; event slices merge peaks and minimum gain without resetting them. Settled disabled meters remain cleared so the original renderer and `lane_mix` arithmetic and summing order remain intact.

The active path finishes trim, distortion, level, velocity and choke for each physical lane, sums all ringing lanes for the track, then applies the single mono strip before pan and sends. Rim/clave and clap/maracas can ring together. Active sends use the currently selected sound controls; disabled sends retain the original per-lane policy. No output/input division is used. Strip-only idle tails and transition/guard release continue on zero input without running an inactive voice or metal bank. Retriggers retain the strip histories.

The focused native suite is `tests/host/run_drum808_strip.sh`, using the accepted `628a9af` source checkpoint for bitwise disabled comparison. Coverage includes 300 variable event slices with all tracks and changed pots/pan/sends/velocities/chokes, all-track ceiling and complete-voice response, paired ringing response and selected sends, cancellation with filter history, meter accumulation and clear, idle transition/tail drain, and bounds rejection. Native suite passes with C99, O2, no FMA contraction and warnings as errors.

Scratch: the active helper holds one 32-float accumulator (128 bytes) alongside the renderer's existing 384-byte voice/metal scratch. It is explicitly noinline so the accumulator has active-call-only lifetime. Native GCC O2 stack-usage reports `d8_render` 608 bytes, active `strip_track_mix` 320 bytes, and `voice_run` 64 bytes (nested; shared strip callee adds its own frame). These host ABI measurements do not establish physical FM1 target stack or cycle acceptance. Combined target stack/resource checks, browser acceptance and physical CPU/device acceptance remain owned by the integration task.
